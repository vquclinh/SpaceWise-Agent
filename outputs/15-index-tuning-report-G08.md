## 3. Measurement Method

For each workload, the benchmark used two scenarios:

- **Before:** the tuned index or tuned index bundle for that workload was
  dropped. Other unrelated schema indexes remained in place because they are
  part of the Phase 1/Phase 2 baseline.
- **After:** the proposed tuned index or tuned index bundle was created.

Each before/after scenario was executed three times after clearing the plan
cache and buffer cache for that scenario. Runtime and logical-read values were
captured from SQL Server plan-cache runtime counters for the tagged benchmark
statements. Execution-plan access paths were captured from
`sys.dm_exec_query_plan` after the statements executed.

Because these are container-local timings, the absolute millisecond values are
environment-specific. The read counts and access-path changes are the stronger
evidence for the index design.

## 5. Tuned Workload 1 - Booking Conflict Check

### Query Surface

The conflict check searches for an existing active booking on the same space
whose reserved interval overlaps the requested interval:

```sql
SELECT TOP (1) b.booking_id
FROM dbo.bookings b WITH (UPDLOCK, HOLDLOCK)
WHERE b.space_id = @space_id
  AND b.status IN (N'Approved', N'CheckedIn')
  AND b.requested_start_time < @new_end_time
  AND b.requested_end_time > @new_start_time;
```

### Before Index

Without `IX_bookings_space_status_time`, SQL Server used
`IX_bookings_space_status_start` and a clustered-key lookup path. That still
returns the correct answer, but it does not match the exact concurrency
predicate and leaves more status/time filtering as residual work.

### Tuned Index

```sql
CREATE INDEX IX_bookings_space_status_time
ON dbo.bookings (space_id, requested_start_time, requested_end_time)
WHERE status IN (N'Approved', N'CheckedIn');
```

### After Index

The after plan used an index seek on `IX_bookings_space_status_time`. This is
the desired access path because the filtered index contains only bookings that
can block a new approval. It also supports SQL Server key-range locking under
`SERIALIZABLE` with `UPDLOCK, HOLDLOCK`.

Measured result: average logical reads dropped from `287.33` to `6.00`, and
average elapsed time dropped from `2.56 ms` to `0.59 ms`.

## 6. Tuned Workload 2 - Room Finder

### Query Surface

The room finder is Query 3 in `outputs/16-analytical-queries-G08.sql`. It
returns spaces that:

- meet the requested capacity;
- are not `TemporarilyClosed` or `Retired`;
- have no overlapping `Approved` or `CheckedIn` booking;
- have no overlapping active `OutOfService` maintenance;
- have at least one available unit for every requested facility.

### Before Indexes

Without the room-finder index bundle, the plan scanned large booking and asset
paths repeatedly while checking each candidate space. The before plan included
clustered scans on `bookings` and `facility_assets`, and broader maintenance
access paths.

### Tuned Index Bundle

```sql
CREATE INDEX IX_roomfinder_capacity_type
ON dbo.spaces (capacity, space_type)
WHERE current_status <> N'TemporarilyClosed'
  AND current_status <> N'Retired';

CREATE INDEX IX_bookings_space_status_time
ON dbo.bookings (space_id, requested_start_time, requested_end_time)
WHERE status IN (N'Approved', N'CheckedIn');

CREATE INDEX IX_maintenance_blocking
ON dbo.maintenance_records (space_id, start_time, completion_time)
WHERE impact_level = N'OutOfService'
  AND status <> N'Completed'
  AND status <> N'Cancelled';

CREATE INDEX IX_assets_location_status
ON dbo.facility_assets (space_id, facility_name, asset_status);
```

### After Indexes

The after plan used indexed anti-probes through
`IX_bookings_space_status_time`, `IX_maintenance_blocking`, and
`IX_assets_location_status`. SQL Server still scanned `spaces` through the
clustered key in this benchmark because the generated dataset has only 82 total
spaces after Phase 1 plus Phase 2 data. That is acceptable: the expensive part
of the query is not the small space catalogue, but the repeated booking,
maintenance, and asset checks.

Measured result: average logical reads dropped from `339,395.33` to `479.67`,
and average elapsed time dropped from `3,814.45 ms` to `845.42 ms`.

## 7. Tuned Workload 3 - Total Approved Booking Hours by Space

### Query Surface

This is Query 1 in `outputs/16-analytical-queries-G08.sql`. It filters approved
lifecycle bookings, verifies an `Approved` decision exists, joins
`usage_sessions` for completed bookings, clips intervals to the semester
boundary, and aggregates approved hours by space.

The benchmark semester was:

```sql
DECLARE @semester_start DATETIME2 = '2025-09-01T00:00:00';
DECLARE @semester_end   DATETIME2 = '2026-01-19T00:00:00';
```

### Before Index

For the before scenario, the reporting-specific indexes on `bookings` were
dropped. SQL Server used broader existing booking indexes such as
`IX_bookings_status`, `IX_bookings_time_range`, and `IX_bookings_space_id`, with
additional work to combine the status, time-range, and space grouping logic.

### Tuned Index

```sql
CREATE INDEX IX_bookings_report_semester_range
ON dbo.bookings (requested_start_time, space_id)
INCLUDE (booking_id, requested_end_time, status)
WHERE status IN (N'Approved', N'CheckedIn', N'Completed');
```

### After Index

The after plan used `IX_bookings_report_semester_range` for the `bookings`
access path. This matches semester-wide reporting better than a space-first
index because the report scans a date range across all spaces.

Measured result: average logical reads dropped from `9,245.00` to `7,114.00`,
and average elapsed time dropped from `82.98 ms` to `40.50 ms`.

## 8. Tuned Workload 4 - Approved Bookings by Weekday and Hour

### Query Surface

This is Query 2 in `outputs/16-analytical-queries-G08.sql`. It filters approved
lifecycle bookings in a semester and groups them by weekday and requested start
hour.

### Before Index

Before the reporting index, SQL Server used the more general booking indexes
`IX_bookings_status` and `IX_bookings_time_range`. These indexes help, but they
do not cover the exact semester reporting shape as directly.

### Tuned Index

The same reporting index from Section 7 is used:

```sql
CREATE INDEX IX_bookings_report_semester_range
ON dbo.bookings (requested_start_time, space_id)
INCLUDE (booking_id, requested_end_time, status)
WHERE status IN (N'Approved', N'CheckedIn', N'Completed');
```

### After Index

The after plan used an index seek on `IX_bookings_report_semester_range` before
grouping by weekday and hour. The index reduces the booking rows read for the
semester window and keeps the needed booking columns covered.

Measured result: average logical reads dropped from `3,306.00` to `2,579.00`,
and average elapsed time dropped from `50.09 ms` to `31.46 ms`.

## 9. Tradeoffs

- `IX_bookings_space_status_time` is required for both performance and
  concurrency. It keeps the approval conflict predicate seekable and helps keep
  SQL Server key-range locks narrow under `SERIALIZABLE`.
- The room-finder indexes add write cost on `spaces`, `bookings`,
  `maintenance_records`, and `facility_assets`, but the read improvement is
  large enough to justify them for the primary room-search workflow.
- `IX_bookings_report_semester_range` improves both selected reporting queries.
  It overlaps partly with `IX_bookings_space_status_start`, so the team should
  keep both only if both access patterns are needed: space-first drill-downs
  and semester-wide reports.
- Indexes do not replace correctness logic. The no-overlap invariant still
  depends on Task 12 transactions and validation triggers; indexes make the
  predicates efficient and reduce lock footprint.

## 10. Conclusion

The benchmark confirms that the proposed Phase 2 indexing strategy meets the
Task 15 requirement:

- the booking conflict check improves from `287.33` to `6.00` average logical
  reads;
- the room finder improves from `339,395.33` to `479.67` average logical reads;
- the total approved-hours report improves from `82.98 ms` to `40.50 ms`
  average elapsed time;
- the weekday/hour heatmap improves from `50.09 ms` to `31.46 ms` average
  elapsed time.

The largest improvement is the room finder, because its untuned version performs
expensive repeated checks across bookings and assets. The reporting improvements
are smaller but still measurable on the 120,000-booking workload, especially
when the semester-range index is used.
